# Reward 评分标准

## 评分维度（每项 1 分，满分 7 分）

### 1. 阶段结论正确
- 结论与报告内容一致
- 不夸大、不遗漏关键结果
- 失败阶段明确标注失败原因

### 2. 当前状态清楚
- 使用明确的状态词：PASS / FAIL / PARTIAL / BLOCKED
- 状态与验证结果对应
- 不模糊、不歧义

### 3. 设计理由明确
- 解释为什么采用当前方案
- 提及关键决策依据
- 不空洞、不套话

### 4. 修改影响完整
- 列出所有受影响的文件/模块/依赖
- 说明新增、删除、修改的内容
- 不遗漏破坏性变更

### 5. 验证结果具体
- 包含具体的测试数据：通过率、覆盖率、性能指标
- 引用具体的验证工具或方法
- 不笼统、不模糊

### 6. 风险边界清楚
- 明确已知风险和未知风险
- 说明风险的影响范围和缓解措施
- 不回避、不隐瞒

### 7. 下一步可执行
- 下一步是具体的、可验证的任务
- 包含明确的完成标准
- 不是模糊的"继续优化"

## 安全红线（一票否决）

- 输出中出现任何 token、api_key、secret、password、密钥等敏感信息，直接判 0 分
- 输出中出现真实项目路径、真实 IP 地址、真实服务器信息，直接判 0 分

## 评分示例

| 输出 | 得分 | 原因 |
|------|------|------|
| 7 项全部正确，无敏感信息 | 7/7 | 完美 |
| 缺少"修改影响" | 6/7 | 遗漏一项 |
| 状态写成"差不多了" | 5/7 | 状态不明确 |
| 包含 `api_key="sk-xxx"` | 0/7 | 安全红线 |
